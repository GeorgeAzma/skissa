# Releases and updates

Part of CLAUDE.md, moved out to keep every session's context small. Read it before working in this area; keep it current.

- **Releases** (`packaging/windows/make-release.py`): a portable zip following the DLL imports, with license texts and SOURCE.txt for the exact tag; DLLs loaded by name go in `LOADED`. Build from `env\_install` (read only) into `krita-deps\release` while no install runs. It is built with `HIDE_SAFE_ASSERTS` off, so `kis_assert.cpp` shows the "internal error" box only in the dev profile.
- **Updates** (`KisSkissaUpdater`): only a release folder (with `skissa-files.txt`) checks GitHub 30 s after start and every 4 hours (`StudioUpdates`), downloads the zip into the profile's `updates` folder (resuming, sha256 checked: an asset without GitHub's `digest` is never taken), unpacks it as `<folder>.update`; on quit `update.ps1` (logging `update.log`) swaps folders by renames, keeping `<folder>.old` (removed by the new version two minutes after it starts, unless it holds the user's files: `removeReplacedInstall`), or moves the contents when the folder can't be renamed (`Move-Contents`). The script that runs is the old version's, so its fixes take effect one update later. A start while a downloaded update waits (in the seconds between quitting and the swap, or after a swap the folder held up) hands it to the swap and ends, the swap then starting the new version (`startWaitingUpdate`, from `main.cc`; not with files to open or Skissa already open); the script takes a mutex (`Local\SkissaUpdate`), so a second one waits and only starts the program, and after a failed swap it starts the version in place with `SKISSA_NO_SWAP` set, so the start doesn't hand off again. Seen in use: Skissa opened again two seconds after quitting ran the old version, held the folder, and its own quit started a second swap. Helpers must start elsewhere than the program folder (`setWorkingDirectory`): Windows won't rename a folder a process works in. Once unpacked, the update's program files are read once in the background (`readProgramFiles`): Windows' virus scan checks each new program file the first time it is opened, which made the first start after an update take 10–40 s instead of 3; the scans survive the folder rename. Restart goes through it (`KisSkissaUpdater::restart`). The command is Update Skissa (`skissa_check_updates`); while downloading its text is the progress, so Find knows it by aliases too. Version: `packaging/skissa-version.txt` (`SKISSA_VERSION`). Test with `KRITA_DEV_UPDATES=<url>` (a JSON like GitHub's, the asset with its `"digest": "sha256:…"`; the zip served over HTTP, e.g. `python -m http.server`, since a file:// download has no status and is dropped) on a release folder run with `KRITA_DEV_PROFILE=1` and `KRITA_DEV_APART=1`, started from its bin folder. That pair has its own single-instance key, so it runs beside the dev build instead of handing itself over.
- **Publishing** (`devtools\release.ps1`, `packaging/skissa-release.py`): from a clean `main`: next patch version (or `-Version`), committed, built, zipped, tagged, pushed, GitHub release (`-NotesFile`, else commit subjects; `-NoPublish` stops at the zip). Only when the owner asks.
- **Translations** (`packaging/skissa-translations.py`): the fork's text gets only translations Krita already has, written to `po-skissa/<lang>.po`; Krita's `po/` stays upstream's, joined at build (`cmake/modules/SkissaTranslations.cmake`). `OTHER_SENSE` lists text used in another sense. Never write translations by hand; rerun after merging upstream or changing text.
